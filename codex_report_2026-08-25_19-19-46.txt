Beer Chronicles homepage timeline-data performance report
Execution time: 2026-08-25 19:19:46 CEST

1. Executive conclusion

SUCCESS. The homepage no longer serializes the complete timeline dataset into its initial HTML/React Server Component payload. A deterministic build-time route now emits the same complete dataset as `/timeline-data.json`, and a small client loader fetches that static asset before mounting the existing `Timeline` component.

The post-Playfair pre-change production homepage measured 914,281 bytes uncompressed, 264,405 bytes gzip-equivalent, with an 868,924-byte `.rsc` file. The clean post-change export measures 21,483 bytes uncompressed, 4,391 bytes gzip-equivalent, with an 11,624-byte `.rsc` file. These are reductions of approximately 97.7%, 98.3%, and 98.7%, respectively.

All 462 active events remain in the exported timeline dataset. Its IDs exactly match the 462 generated permanent-event directories, and the clean sitemap contains 462 event URLs. No event content or database record was changed.

The separate JSON is 883,593 bytes uncompressed and approximately 276,073 bytes gzip-equivalent. This change therefore isolates the critical initial document and makes the large dataset independently cacheable; it does not claim to reduce cold-load total transfer materially. The JSON is also no longer escaped inside the React flight protocol and is parsed only after the LCP shell has hydrated.

No Lighthouse improvement is claimed because Lighthouse/PageSpeed was not available locally.

2. Pre-change architecture

`src/app/page.tsx` was an async server component that performed three build-time Supabase reads:

- all active event rows through `events.select("*")`;
- all tags;
- all event/tag relations, paged in groups of 1,000.

The page joined tags onto every event, sorted all events, calculated visible tags and year bounds, and passed the complete object graph to the client `Timeline` component. Because `Timeline` uses `useSearchParams`, the static HTML displayed a small Suspense fallback, but React still serialized all event props into inline flight-data scripts.

After hydration, `Timeline` filtered and sorted the array and rendered every matching event through `filteredEvents.map(...)`. With no active filter, this mounted every timeline card.

`TimelineModal` received complete event objects synchronously. `EventDetailContent` used their full descriptions, sources, tags, and identity data. Related events were calculated in the client from the same array. Permanent event pages independently use `src/lib/eventPageData.ts`; they are statically generated and were not coupled to the homepage client payload.

3. Field-dependency analysis

The complete dependency map established before implementation was:

- `id`: React keys, selected/related-event identity, modal scroll reset, permanent links, correction links, tag/storyline section IDs.
- `title`: title search, card title, modal title, related-event title, accessible card label, permanent slug/link, correction context.
- `description`: full-text search, card preview truncation, full modal content, related-event preview.
- `event_date`: timeline year fallback, chronological sorting, date formatting on cards/modals/related entries.
- `historical_year`: prehistoric/BCE year placement, sorting, range filtering, formatted dates, related-event distance.
- `date_precision`: exact/month/year/decade/century date formatting.
- `category`: category filtering, card badge, modal badge, related-event scoring.
- `tags` (`id` and `name`): tag counts, all/any tag filtering, milestone badge, Storyline links, modal tag links, related-event scoring, direct URL resolution.
- `sources`: modal source list only on the homepage, plus permanent-page content in the separate permanent-page architecture.
- `image_url`: not currently rendered by homepage cards or modals, but remains part of the complete event contract and is used by permanent-event social metadata/structured data.
- `created_at`: not currently rendered in the homepage modal, but remains part of the event contract and permanent-page structured data.
- `deleted_at`: used by the database filter and remains null in exported active rows; not rendered.
- all tags: direct URL resolution, including hidden tags, and filter URL serialization.
- visible tags: dropdown contents, limited to tags on at least three active events.
- `minYear`/`maxYear`: initial range state, slider bounds, reset/default detection, and direct URL clamping.

Behavior mapping:

- Filtering: category, chronology fields, tag IDs, title, and complete description.
- Sorting/newest/oldest: `event_date` and `historical_year`.
- Cards: title, description, date fields, date precision, category, tags.
- Modal: all card fields plus complete description, sources, tags, and permanent/correction URL identity.
- Related entries: IDs, tags, category, chronology fields; related previews also need title and description.
- Random Discovery: the complete event array and all modal/detail fields, because any event can be chosen.
- Query URLs: full tag name/ID mapping plus category, range, tag mode, and search state.

Because free-text search intentionally searches full descriptions, a genuinely summary-only initial dataset cannot preserve current search semantics without a separate search index or without loading full description text before the timeline becomes interactive.

4. Alternatives considered

Option A — summary and on-demand detail datasets

Potentially reduces the first timeline-data fetch by omitting sources and most description text. It was not chosen for this first step because full descriptions are required for existing search, card previews, related previews, and immediate modal content. A separate full-text index plus per-event detail loading would add state, failure modes, loading UI, rapid-navigation races, and cache coordination. Fetching details on first modal open would directly risk degrading a currently synchronous modal experience.

Option B — generated static/cacheable JSON

Chosen. It removes the entire dataset from initial RSC serialization, works with `output: "export"`, is produced deterministically during the existing build, can be cached independently by the browser/host, and lets the existing Timeline receive the exact same data shape. It adds one fetch but no server requirement.

Option C — reuse per-event static pages

Rejected. Permanent pages expose complete human-readable HTML and structured data, not a stable client-data API. Reusing them would require parsing HTML and potentially hundreds of requests, would complicate related navigation, and would be less maintainable than one explicit static dataset.

Option D — direct browser-to-Supabase loading

Rejected. It would shrink HTML but add a runtime backend dependency to the core timeline, weaken deterministic static deployment behavior, complicate failure/caching semantics, and offer no advantage over a build-generated asset.

Option D — server-only API or Next runtime endpoint

Rejected because the repository uses static export and must not acquire a permanent Next.js server requirement.

Initial-card virtualization or pagination

Rejected for this task because it changes core discoverability, browser-find/accessibility behavior, or visible timeline mechanics. CSS containment/content-visibility was also left untouched because no browser measurement was available to establish benefit or validate scroll geometry.

5. Chosen architecture and rationale

The chosen architecture is one static, complete timeline dataset:

1. `getHomeTimelineData()` performs the previous homepage build-time query/join/sort/count logic.
2. `src/app/timeline-data.json/route.ts` is forced static and returns that data through `Response.json()` during export.
3. The server-rendered homepage contains only the visual shell and `TimelineDataLoader`.
4. The loader fetches `/timeline-data.json` after hydration.
5. While fetching, it renders the same `h-20` space used by the previous Suspense fallback.
6. Once loaded, it passes the unchanged event/tag/year props to the existing `Timeline`.
7. If loading fails, it shows an accessible error instead of mounting a partial or corrupt timeline.

This is the smallest solution that removes all historical event data from the initial RSC payload while retaining full search and synchronous modal behavior once the timeline is visible. It does not split summary/detail data because that materially different architecture requires product decisions about search indexing and modal loading behavior.

An explicit event-ID ordering was added to the build query. It makes the database read deterministic before the existing chronological sort and also ensured a clean local build invalidated an inconsistent incremental-cache artifact. The final clean export was validated against active IDs, permanent pages, and sitemap URLs.

6. Files changed

Task source files:

`src/app/page.tsx`

- Why: it was the source of the oversized inline RSC props.
- What: removed Supabase reads, joins, counts, year calculation, and complete props from the server page; replaced the Timeline props with `TimelineDataLoader` inside the existing Suspense location.
- Necessity: prevents event records from entering homepage server-component serialization.
- Regression risk: the timeline now begins loading through a static fetch after hydration. The header, Storylines LCP teaser, footer, metadata, and component placement are unchanged.

`src/lib/homeTimelineData.ts`

- Why: the existing homepage data assembly needed a reusable build-only location for the static route.
- What: moved the original event/tag query, paged relation query, joins, visible-tag threshold, chronological sort, and year bounds into `getHomeTimelineData`; added deterministic event-ID query ordering and a typed `HomeTimelineData` contract.
- Necessity: gives the static JSON route the same complete data shape previously passed inline.
- Regression risk: query/assembly behavior could diverge from the previous page if modified later. The implementation was copied conservatively and its final IDs/counts were verified.

`src/app/timeline-data.json/route.ts`

- Why: static hosting needs a generated data representation outside HTML/RSC.
- What: added a force-static GET route returning `HomeTimelineData` as JSON.
- Necessity: creates `out/timeline-data.json` during `next build` with no runtime server.
- Regression risk: a failed build-time Supabase read fails the build instead of publishing an incomplete timeline asset, which is preferable to silently incomplete data. The non-hashed URL relies on normal HTTP revalidation rather than immutable caching.

`src/components/TimelineDataLoader.tsx`

- Why: the browser needs to acquire the exported dataset before mounting the unchanged Timeline.
- What: added abortable one-time fetch state, the existing-height loading placeholder, explicit error output, and unchanged Timeline prop forwarding.
- Necessity: keeps event data out of RSC while retaining all Timeline functionality.
- Regression risk: on an uncached first visit, timeline controls/cards appear after the JSON response rather than immediately after hydration. Modal interaction is not degraded because cards are not offered until complete details are available. Failed fetches now produce a visible error and no partial interface.

No existing Timeline, filtering, modal, card, permanent-page, metadata, sitemap, structured-data, styling, typography, or historical-content file was changed.

11. Known limitations

- The first uncached timeline view now depends on downloading and parsing an approximately 884 KB raw/276 KB gzip JSON asset before controls and cards appear. The server-rendered header and LCP teaser remain immediate.
- The dataset URL is stable rather than content-hashed. It benefits from normal browser/HTTP caching and revalidation, but must not be served with an immutable lifetime across deployments.
- Cold total bytes are not reduced materially; this step specifically removes data from the critical HTML/RSC response and separates caching/parsing.
- All 462 cards are still mounted after data loading. Whether this remains a meaningful performance bottleneck needs post-deployment measurement.
- Visual and interactive browser automation was unavailable.
- A summary/detail split could reduce the JSON transfer, but preserving full-description search and synchronous modal behavior requires a deliberate architecture decision (search index, detail granularity, prefetch policy, error/loading UX). That ambiguous expansion was intentionally not implemented.
- During verification, an incremental local build briefly mixed a 453-event cached artifact with 462 permanent pages. A deterministic event-ID order was added, ignored build artifacts were moved aside, and the final clean network-enabled build produced a coherent 462/462/462 JSON/page/sitemap result. Deployment builds should continue to run in a clean environment.

13. Recommendation for human review

The implementation is ready for human review as a conservative first payload step. It achieves the primary technical objective—materially smaller initial HTML/RSC—without removing events, changing event data, changing filters, changing modal content, modifying permanent pages, introducing a server, or redesigning the interface.

Before committing, a human reviewer should confirm the deployment platform serves `/timeline-data.json` with compression and revalidation-appropriate cache headers, and should perform browser smoke tests for first timeline load, direct query URLs, filters, Random Discovery, cards, modal navigation, related entries, permanent links, and simulated JSON-request failure.

After deployment, run multiple mobile PageSpeed Insights tests and compare medians with the stated 69 / 3.0 s FCP / 5.9 s LCP / 60 ms TBT / 0 CLS / 5.2 s Speed Index baseline. Do not proceed immediately to virtualization or summary/detail splitting unless those measurements and browser traces show the remaining bottleneck and justify the added complexity.
